# Verification playbook

This is where the defects that actually invalidate papers are found. It is also the phase that gets
skipped, because it is slower than reading and it requires opening the code.

The organising idea: **a paper is a set of claims about artifacts.** Every number is a claim that some
computation produced it. Verification means following each number back to the thing that produced it and
checking that it did.

Anything you cannot trace is a finding. Not "probably fine" — a finding. In practice, untraceable numbers
split roughly evenly between stale values left over from an earlier analysis and genuine transcription
errors, and you cannot tell which without checking.

---

## 1. Build the claim ledger

Before checking anything, enumerate. Go through the abstract and conclusions and number every assertion.
Then extract every numeric literal in the prose. For each, record where it should come from.

This inventory is the audit's backbone. Work it to exhaustion; do not sample.

## 2. Prose against tables against figures

Every number quoted in the running text should appear in a table or figure, and match.

Common failures:
- The text quotes a value that was updated in the table but not in the prose.
- The abstract carries numbers from an earlier run of the analysis.
- A figure's caption states a value the figure does not show.
- Rounding differs between text and table, so they disagree in the last digit while both being "right".

**The durable fix.** When numbers are typed by hand into the manuscript, they *will* drift — not might.
Have the analysis pipeline emit a macro file, and have the text reference macros rather than literals:

```latex
% generated by the pipeline; never edited by hand
\newcommand{\ResultAccuracy}{0.847}
\newcommand{\ResultCI}{[0.821, 0.873]}
```

```latex
accuracy of \ResultAccuracy{} (95\% CI \ResultCI)
```

This makes drift structurally impossible instead of merely absent today, and in a multi-language paper it
keeps versions identical by construction. Recommending this is often the single highest-value change in an
audit, and it is cheap.

## 3. Tables against each other

The same quantity reported in two places must agree. When it does not, there are exactly two possibilities
and both are findings:

- **A bug.** Two code paths compute the same thing differently. One is wrong.
- **A naming collision.** They are different quantities with the same label. The paper is misleading.

Do not accept "they are computed slightly differently" as a resolution without establishing which is
correct and why the other exists.

**A worked example of what this catches.** A manuscript reported a strategy's resource use as 60.3 units in
its main table and 310.6 units in its uncertainty table. Both came from the same pipeline. The main table
integrated usage against the model's *default heuristic policy* rather than the *optimised policy actually
applied*, because the accounting function received the trajectory but not the policy. The paper's headline
claim — better outcomes with fewer resources — was an artefact of this. Two numbers disagreeing by a factor
of five was the only visible symptom.

## 4. The paper against the code

Read the implementation. Do not infer it from the methods section — the methods section describes what the
authors meant to do, and the audit is about what the code did.

Check specifically:

- **The estimator or objective.** Does the loss, likelihood, or update rule match the equation in the text?
- **Denominators and normalisation.** Population, sample size, time base, unit conversion.
- **Which data went in.** Filters, exclusions, and the split, compared against what the text says.
- **Configuration actually used.** Defaults in a class definition are often overridden by a config file at
  run time. The paper may document the defaults while the results came from the overrides. Check the run
  artifacts, not the source defaults.
- **Post-processing.** Clipping, smoothing, outlier removal applied but undocumented.

Where a result file records the settings used, compare it against the paper directly. That comparison takes
a minute and regularly finds discrepancies.

## 5. Internal statistical coherence

Cheap checks with a high hit rate:

- **A point estimate must lie inside its own interval.** When it does not, two different computations are
  being presented as one.
- **Totals equal the sum of parts**; percentages sum to 100 where they should; subgroup sizes sum to n.
- **Differences and ratios recompute.** Take the two reported values and derive the reported difference.
- **Reported n is consistent** across text, tables, figures and the flow diagram.
- **Degrees of freedom match the stated design.**
- **Orders of magnitude are plausible** given the units. This catches unit errors, which are common and
  embarrassing.

## 6. Arithmetic on derived quantities

Recompute anything the paper derives. Rates from counts and denominators, cost per unit, relative changes,
annualisations, discounting. State the recomputation in the audit report so the authors can check your check.

## 7. Cross-language parity

For multi-language papers, run `scripts/crossref_versions.py`. It compares section structure, counts of
equations, tables and figures, label sets, and numeric literals.

Divergence is nearly always one of:
- A correction applied to one language and not the other.
- A table regenerated for one version only.
- A translated number using a different decimal convention — and note that `1,234` means different things
  in English and Spanish, which is a real source of silent corruption.

Parity is not optional. A paper is not ready if only one language version is.

## 8. Figures

- Does the figure show what the caption claims?
- Are axes labelled with units, and is any log scale identified as such?
- Do error bars have a stated meaning — standard deviation, standard error, or confidence interval? An
  unlabelled error bar is uninterpretable.
- Are sample sizes shown or stated?
- Is colour the only channel distinguishing series? That fails for colour-blind readers and in print.
- Does the figure's data match the table's?

Load the **dataviz** skill before rebuilding any figure.

## 9. Bibliography

Run `scripts/audit_bibliography.py`, then check by hand what a script cannot:

- Do the load-bearing citations actually support the claims attached to them? Fetch and read them.
- Are preprints marked as preprints?
- Are retracted papers cited? Search the DOI.
- Do the same works appear identically across language versions?

---

## Recording what you verified

The audit report needs a verification section stating what was checked, not merely what was found. "No
inconsistencies found between prose and tables" is a result, and it tells the authors and any future
reader which parts of the paper have been examined and which have not.

Be explicit about what you could **not** verify — numbers whose source data was unavailable, analyses that
could not be re-run. Unverifiable is a legitimate state; unexamined is not.
